# ADR-0002: v1.0 success criteria — "First shipped version"

**Status:** Accepted
**Date:** 2026-04-29
**Deciders:** Carter King (ck22coding)
**Supersedes:** None
**Companion:** [Phase 5 plan — Skill-compliance rule additions](~/.claude/plans/phase-5-skill-compliance-additions.md) (proposals deferred post-v1.0)

---

## Context

Through the finish-the-factory wave (Stages 9–12), an implicit maximalist v1.0 framing had accumulated: v1.0 would ship only after all open decisions were resolved, body-size band contradictions were reconciled, skill-compliance rule additions were implemented, and CI/pre-commit hooks were wired. That framing was never written down; it accreted in planning notes and conversation context.

By mid-session 2026-04-29, the factory had cleared the substantive bar: 9 sub-skills shipped, driver-integrated, and gate-passing via the BP-003 meta-skill exception; the compliance gate applying its own rubric cleanly to all 9 of its own artifacts (bonus-sweep gate-clean invariant, 9/9); a 367/367 test gauntlet across 7 sub-skill suites; and 2 real client deliveries — acme-board-memo (local-only) and discovery-call-prep (GitHub-PRIVATE with collaborator) — proving hands-off authoring end-to-end against two distinct install profiles.

Carter mid-session 2026-04-29 narrowed the framing explicitly: v1.0 means "first shipped version." It tags what is working today rather than waiting for every open decision to close. The three residual open items (body-size band reconciliation, Stage 13 rule additions, CI/hooks) are real but do not improve the factory's ability to author and install client skills. Tagging v1.0 against the proven baseline lets that work land as additive v1.x improvements without bundling pressure.

---

## Decision

**v1.0 is defined as the first shipped version of the Skill Factory, tagged against the state proven by the bonus-sweep gate-clean invariant and 2 real client deliveries.**

### Required for v1.0 (the ship-as-is checklist)

1. 9 sub-skills shipped + driver-integrated + gate-clean via BP-003 meta-skill exception — skill-compliance, skill-spec-validator, skill-factory (driver), skill-frontmatter, skill-phase-designer, skill-references-scaffolder, skill-cron-observability, skill-signed-handoff, skill-compliance-gate. **(ALREADY MET)**
2. Driver canaries green: `phase_lint` reports "10 step(s) detected in sequence 1..10"; `references_lint --strict-two-level` reports "10 phase director(s) inspected" + "references/ is flat with 5 .md file(s)". **(ALREADY MET)**
3. Test gauntlet 367/367 across 7 sub-skill suites (22 frontmatter + 33 phase-designer + 51 references-scaffolder + 28 cron-observability + 36 signed-handoff + 163 skill-factory + 34 compliance-gate). **(ALREADY MET)**
4. At least 2 real client deliveries proving end-to-end hands-off authoring: acme-board-memo (Stage 11c, installed at ~/Projects/acme-claude-skills/, local-only — gh opted out via spec) and discovery-call-prep (Stage 11e, installed at ~/Projects/optimal-skills/, GitHub-PRIVATE). **(ALREADY MET)**
5. Frame C documented (ADR-0001 already shipped) and v1.0 framing locked (this ADR). **(ALREADY MET)**
6. Phase 5 open-decision proposals captured in companion file ~/.claude/plans/phase-5-skill-compliance-additions.md. **(ALREADY MET)**
7. Phase 6 — live verifications: Stage 11d test-acme cleanup (Carter manual GitHub UI delete + local rm), live `gh_ensure_local_origin` smoke (Stage 12 item 4 — re-run discovery-call-prep with spec flipped to remote=yes), live Agent self-bootstrap E2E (Stage 10c-deferred follow-up). **(KEYBOARD-REQUIRED)**
8. Phase 7 — close-out artifacts: CHANGELOG entry, VERSION bump to 1.0.0, README polish, git tag v1.0. **(KEYBOARD-REQUIRED)**

### Deferred post-v1.0 (known issues / follow-ups)

1. **BP-006 ↔ Principle E body-size band reconciliation.** Driver SKILL.md sits at 130 body-lines — within Principle E's ≤150 thin-director ceiling but below BP-006's 180-220 monolith band. The contradiction is dormant doc-debt; compliance_check.py is informational (not strict-enforcing) on the 180 floor, so the bonus-sweep gate has been 9/9 PASS throughout. Defer reason: cosmetic; no runtime effect; opens a re-litigation surface that would slow the v1.0 tag.
2. **Skill-compliance rule additions.** Two checks proposed in the companion Phase 5 plan doc: BP-033 leakage check and cross-scope meta-skill check. Defer reason: gate is 9/9 PASS, no live leakage; hardening prevents regression but does not fix a current bug.
3. **CI on PRs (.github/workflows/compliance.yml).** Defer reason: the local gauntlet runs fast enough (≤30s) that human-in-the-loop pre-push is sufficient pre-v1.0; forgetting to run the gauntlet has not surfaced as a real loss.
4. **Pre-commit hook to enforce HUB.md updates.** Defer reason: the two-commit pattern (`<work>` + `HUB:` stub) has held across 5 consecutive waves; convention discipline is currently sufficient.
5. **Stage 11d test-acme repo deletion.** Carter created ck22coding/test-acme-claude-skills during Stage 11d; the gh token lacks delete_repo scope so UI deletion is pending. Defer reason: not a code issue; one-line manual cleanup note for the v1.0 release process.

### Why this framing

The original maximalist framing was never explicitly decided — it accumulated implicitly. Surfacing and rejecting it mid-session is a clarifying act, not a scope cut. The factory's primary thesis — hands-off authoring of installable client skills, gate-clean by self-application of its own rubric — is proven. Waiting for BP-006 reconciliation, Stage 13 rule additions, or CI wiring would push the v1.0 tag by ~3–5 stages without adding any functional capability.

The 2 real client deliveries are structurally different: acme is local-only (no gh repo), discovery-call-prep is GitHub-PRIVATE with a collaborator. Those two profiles together cover the install-destination decision space the factory needs to validate before v1.0. Additional client deliveries before tagging would not prove anything structurally new.

The 38 BPs (12 Universal / 11 Conditional / 15 Meta), the 9/9 bonus-sweep invariant, and 367/367 tests represent a stable pattern corpus. Tagging v1.0 now anchors the CHANGELOG and makes subsequent additions clearly additive. The deferred items are improvements, not corrections.

## Alternatives considered and rejected

### Alternative A — Maximalist v1.0 (resolve all open decisions first)

Would require BP-006 ↔ Principle E reconciliation, Stage 13 rule additions (BP-033 leakage check + cross-scope meta-skill check), CI wiring on PRs, and pre-commit hook for HUB.md. Net result: the v1.0 tag slips by approximately 3–5 stages with no functional gain over today's factory. The gate is already 9/9 PASS; the factory already authors and installs client skills hands-off. Resolving the doc-debt and hardening the gate are valuable in isolation, but they do not constitute what "first shipped version" should mean. Rejected.

### Alternative B — Pre-release v0.9.x indefinitely

Keeps everything pinned as "almost ready." Costs: no clear "this works" signal for downstream consumers; CHANGELOG has no anchor; the deferred items create an implicit pressure to bundle before ever tagging. Rejected because the factory functionally meets v1.0 today — "v0.9.x indefinitely" would be accurate only if something were broken or structurally incomplete, and neither is true.

### Alternative C — Defer v1.0 until 5+ client deliveries

The sample-size argument would require authoring at least 3 more client skills before tagging. Rejected because the existing 2 deliveries already span both primary install profiles (local-only and GitHub-PRIVATE with collaborator). Additional deliveries before v1.0 prove nothing structurally new about the factory's hands-off authoring capability. More deliveries will happen as v1.x work — they should inform v1.1 enhancements, not gate v1.0.

## Consequences

### Positive

- Clean v1.0 tag against a known-stable baseline; the CHANGELOG's starting point is unambiguous.
- Follow-up work (Stage 13+ rule additions, body-size band reconciliation, CI) lands as v1.x improvements without bundling pressure or timeline coupling.
- The CHANGELOG's "Known issues / post-v1.0 follow-ups" section is meaningful (anchored to the deferred list above), not aspirational.
- The 2 real client deliveries become v1.0 evidence rather than in-progress samples.

### Negative

- v1.0 ships with documented contradictions (BP-006 ↔ Principle E body-size band). Future readers may trip on the body-size guidance until the reconciliation lands. **Mitigation:** this ADR enumerates the contradiction explicitly with its defer rationale; the companion Stage 14 follow-up tracks the reconciliation.
- v1.0 ships without CI. Self-discipline must hold until the post-v1.0 CI lands. **Mitigation:** the gauntlet command is already fast (≤30s) and lives in HUB.md's Test Recipe; the failure mode (someone pushes without running the gauntlet) has not occurred across 5 consecutive waves.
- "First shipped version" framing may set an expectation that the factory is more polished than it is. **Mitigation:** the v1.0 README's "Status and roadmap" section lists what is not yet shipped; this ADR's deferred list is the authoritative post-v1.0 backlog.

### Neutral

- Frame C stays the trait model (ADR-0001 unaffected by this decision).
- The 38 BPs (12 Universal / 11 Conditional / 15 Meta) stay — no BP added or removed for v1.0.
- The two-level director hierarchy (Principle F, Stage 9.0) stays — no driver shape change for v1.0.
