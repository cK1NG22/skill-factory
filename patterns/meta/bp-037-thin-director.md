# BP-037: Thin top-director SKILL.md for phased orchestrators

**Source:** 2026-04-24 Stage 9.0 (skill-factory two-level director hierarchy; driver body 201 → 113 lines); 2026-04-27 Stage 11e (driver compaction back to 130 after Phase 9 wiring); promoted from `feedback-director-file-thinness.md`
**Category:** File structure (Meta — factory architecture)

**Why:** A monolithic SKILL.md that inlines per-phase mechanics forces readers to skim past 200+ lines of orchestration detail to understand the high-level flow; phase-specific changes become diff-noisy because every edit touches the same big file. A two-level director hierarchy keeps the orchestration *shape* immediately legible — the top SKILL.md is a numbered list of pointer-steps, each one paragraph long — and isolates phase-specific changes to that phase's `director.md`. Pre-Stage-9 the skill-factory driver was 201 body-lines; the rewrite dropped it to 113, and per-phase changes now happen in isolated phase directors without re-reading the whole top file. The same pattern recurs whenever a skill has a long sequential pipeline.

**When applicable:** Phased orchestrator skills with 5+ sequential phases each invoking a sub-component (the skill-factory driver is the canonical example — 10 phases at 130 body-lines). Skip for simple single-procedure leaf skills (e.g., `skill-frontmatter`, `skill-phase-designer`) — those stay flat with one Procedure and no phase sub-tree. The factory's own sub-skills are the negative examples: they enforce factory rules but don't themselves need this shape.

**Enforced by:** `skill-references-scaffolder/scripts/references_lint.py --strict-two-level` (walks `phases/<N>-*/director.md` and reports total phase directors inspected; the canary `"10 phase director(s) inspected"` doubles as a structural assertion for the skill-factory driver). The soft 150-body-line cap on the top SKILL.md is informational — `skill-compliance` reports `info` (not failure) for thin top directors below the historical 180–220 band, leaving the cap as a guideline rather than a hard gate.

**Correct:** Top SKILL.md Procedure step: `9. Materialize the assembled skill. Read \`phases/09-materialize/director.md\`.` (one imperative line per step, with trait-gated steps adding a tail clause `... when \`<trait>.fires\` (Pattern A); else skip to Step N+1.`). The director then orchestrates the materializer, parses verdicts, and handles BLOCKERs. Cross-phase mechanics (Agent-spawn boilerplate, trait-gating, invocation contracts) live in top-level `references/`; phase-scoped mechanics live in `phases/<N>-*/references/`.

**Incorrect:** Top SKILL.md Procedure step inlines `9. Materialize. Run \`materialize_skill.py --slug <slug> --assembled-path <path>\`, parse the JSON verdict, branch on \`installed: true\` vs \`installed: false\`, on BLOCKER print the message and STOP, ...` — 30 lines of Phase-9 mechanics that should live in `phases/09-materialize/director.md`. Future phase changes touch the same file as every other phase, churning the diff and obscuring the overall flow.
