# BP-038: Self-bootstrap acceptance criterion for spec-driven authoring tools

**Source:** 2026-04-24 Stage 9c (skill-factory self-bootstrap verification — first run); 2026-04-27 Stage 10c (BP-003 meta-skill exception + gate-verdict-match invariant); promoted from `feedback-self-bootstrap-invariant.md`
**Category:** Verification & evaluation (Meta — factory acceptance)

**Why:** A spec-driven authoring tool that cannot reproduce itself from its own spec has not actually proven its abstractions hold. Self-bootstrap is the strongest possible "the tool works" signal — the tool eats its own dogfood and produces lint-clean output. Failure modes self-bootstrap catches that single-trait fixtures miss: trait-interaction bugs (Stage 9b's pre-scaffold gap surfaced via the `has_phases ∧ has_references` omnibus), recursive description quirks (the factory's own spec leaked "cron" / "/skill-X" mentions into trait verdicts and required spec-side neutralization across two iterations), and meta-vs-client BP exceptions (the BP-003 `<company>-<slug>` rule false-positived on the factory's own slug, which led directly to the `meta-skill: true` marker shipped in Stage 10c).

**When applicable:** Any spec-driven authoring tool — factories, generators, scaffolders. NOT applicable to client skills (which don't author other artifacts) or leaf utilities. The criterion is permanent — once a tool's wave ships, the self-bootstrap fixture stays in the repo and runs on every subsequent change as a regression net.

**Enforced by:** A `fixtures/self-bootstrap/<tool>-spec.md` describing the tool in client-spec form, plus a `scripts/self_bootstrap_diff.py` that runs the tool against this spec in an isolated workspace (`git worktree add` for code-modifying tools), writes to a scratch dir, and reports: which sub-components fired, per-artifact lint verdicts, section-shape match (e.g., Procedure step count delta = 0), file-count delta within tolerance, and gate-verdict match — regenerated AND committed must both PASS, with backward-compat fallthrough for pre-Stage-10b runs (the Stage 10c addition). Tiebreaker rule on divergence: committed code is authoritative; the spec updates to match — UNLESS the committed code violates a committed BP, in which case fix the code first, then re-verify.

**Correct:** `skill-factory/skill-factory/fixtures/self-bootstrap/skill-factory-spec.md` describes the factory in the same client-spec format clients use. `skill-factory/skill-factory/scripts/self_bootstrap_diff.py` runs the factory against that spec and reports `pass` when 3 expected sub-skills fire, all isolated Sonnet Agents produce lint-clean output first attempt, Procedure step count delta = 0, and gate verdicts match between regenerated and committed. The `meta-skill: true` marker (BP-003 §"Meta-skill exception") tells the gate to skip Check 14 — the factory cites its own meta-BPs legitimately.

**Incorrect:** Factory ships without ever running itself against its own spec. First time anyone attempts a meta-skill spec, BP-003's name-rule false-positive emits slug `skill-factory-skill-factory` instead of `skill-factory` — caught months later by chance instead of at Stage 9c. By that point the meta-vs-client distinction has propagated into multiple sub-skills' fixtures and unwinding it is expensive.

**Cross-reference:** BP-003 §"Meta-skill exception (Stage 10c)" — the meta-skill marker emerged DIRECTLY from running the self-bootstrap; the BP-003 carve-out is part of this BP's enforcement chain. BP-029 (build incrementally — self-bootstrap is the LAST stage of a tool's wave, after every sub-component has shipped, never the first).
